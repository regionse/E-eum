# 잇다 — 실측 기록

**이 파일은 「잰 것」만 담는다.** 계획·의견·설계 논의는 다른 문서에.
발표 자료 뒤에 붙일 근거 묶음이다. 새 측정이 나오면 **아래에 덧붙인다**(지우지 않는다).

---

## ★★★ 기록 규칙 (2026-08-09 · 반드시 지킨다)

**모든 실측 기록에는 «얻을 수 있는 정보를 전부» 적는다.** 요약하지 말고, 나중에 필요할까 봐
망설이지 말고 남긴다. 지금 안 적으면 **다시 재야 하고, 그때는 조건이 달라져 있다.**

| 반드시 적을 것 | 왜 |
|---|---|
**모델명·버전** | 값이 모델에 매인다. 「gemini-3.1-flash-lite」처럼 정확히 |
**Pricing** | $/1M 입력·출력·캐시읽기. **직접 찾아 확인한 값**을 적는다 |
**토큰 수** | 입력·출력·캐시(`cachedContentTokenCount`)·사고. 호출 수도 |
**환산 비용** | 원화. 적용한 환율도 함께 (예: $1=1,380원) |
**사용자가 실제로 친 말** | 요약 금지. **원문 그대로** |
**AI 가 실제로 낸 답** | 자르지 말 것. 자를 거면 «몇 자에서 잘랐는지» 표시 |
**중간 산출물** | 슬롯·종류·근거·action·검색어·후보 목록·판정값 |
**측정 조건** | 프롬프트 길이 · 캐시 여부 · 몇 번째 턴 · 온도 · 어떤 경로 |
**측정 도구** | 어떤 스크립트로 쟀나. **자가 틀릴 수 있다** |

⚠ **자를 때는 자른다고 적는다.** 2026-08-08~09 하루에만 «자» 오류가 아홉 번 났고,
  그중 셋이 **출력을 잘라 놓고 시스템 탓으로 오해한 것**이었다(`[:76]` · 채점 낱말 ·
  응답 전체에서 낱말 찾기). 자른 사실을 안 적으면 다음 사람이 같은 함정에 빠진다.

⚠ **비용은 추정과 실측을 «반드시» 구분해 적는다.** 2026-08-09 에 「턴당 1.3원」을 밤새
  반복해 말했는데 실측은 **2.56원**이었다(2배). 추정이면 「추정」이라고 못 박는다.

세 문서는 역할이 다르고 **같은 용어·같은 개수**를 쓴다:

| 문서 | 답하는 질문 |
|---|---|
`기술스택_잇다.md` | **무엇이 있고, 무엇이 켜져 있나** (상수·스위치·기본값) |
`여정_잇다.md` | **언제 무엇이 도는가** (시간 순) |
**이 문서** | **재봤더니 얼마였나** (측정치·근거) |

⚠ 세 문서 모두 코드를 **함수명으로** 가리킨다. 줄 번호는 쓰지 않는다 —
`itda_core.py` 가 커지면서 예전 판의 번호가 약 530줄 밀려 길잡이를 못 했다.

⚠ 아래 측정치는 **잰 시점의 사실**이다. 그 뒤 코드가 바뀌었을 수 있으니
숫자를 발표에 쓸 거라면 해당 검사 도구를 한 번 더 돌릴 것.


`_norm_evade`는 자모·라틴을 **일부러 남긴다**(`'ㅅㅂ'`·`'tlqkf'` 영타 우회 때문에).
그래서 하나로는 서로의 사각을 못 메운다. **정규화를 셋으로 나눴다.**

| 정규화 | 하는 일 | 잡는 것 |
|---|---|---|
`evade` | 공백·숫자·기호 제거 + 반복 축약 | 「대 마 초」「씨1발」 |
`compose` | 분해 자모를 완성형으로 결합 | 「필ㄹㅗ폰」「섹ㅅㅡ」 |

한글 난독화 분류는 KOTOX(arXiv:2510.10961, 프리프린트)의 음운/도상/구문에 대응한다.
「대 마 초」는 2017년에 보고된 기법이다(Hosseini 외, Perspective API 우회).

**작업 중 오탐을 두 번 냈다가 잡았다** ★

## 3-1-a. TOP% 는 «무엇을 기준으로 재느냐»가 전부다 ★

같은 이름이지만 완전히 다른 신호다.

```
                    Vtop%(항목)   Ctop%(묶음)
용접                   0.313    →   1.000      ← 정반대
자동차 고치고 정비하는 일  0.252    →   1.000
```

「CO₂용접·로봇용접·피복아크용접」은 **항목으로 재면 서로 갉아먹어** 1위가 31%밖에 안 되지만,
**묶음으로 재면 「금속재료」 하나가 100%**다. 그래서 11/14 ↔ 13/14로 갈린다.

## 3-1-b. 두·세 신호 조합

```
V & C          14/14
V & Rmax       14/14
C & Rmax       14/14
V & C & Ctop  (다수결)  14/14
V & C & Rmax  (AND/다수결) 14/14
V & C & Ctop  (AND)     13/14   🔴 Ctop 이 「손으로 만드는 일」을 착지로 끌어내림
```

**Ctop 을 AND 로 더하면 오히려 «떨어진다».** 그래서 안 쓴다.

## 3-1-c. ★★ 정확도보다 «마진»이 중요하다

「몇 개 맞았나」는 14케이스에서 쉽게 뒤집힌다. **임계값을 어디에 둬도 되는 구간의 폭**이
실제 견고함이다.

| 방식 | 안전 구간 폭 |
|---|---|
`C` 단독 | LAND 최대 0.283 / CHIP 최소 0.317 → **0.034** |
`Ctop` 단독 | LAND 최소 0.906 / CHIP 최대 0.943 → **−0.036 (겹친다)** ← 원리상 못 가름 |
**`V AND C`** | LAND 최대 **0.000** / CHIP 최소 **0.317** → **0.317** (10배) |

**V 게이트를 통과한 것만 C 로 보면 그 구간이 통째로 빈다.** 경계 케이스(간호조무사 C=0.283)는
V 가 이미 착지로 보내서 C 비교에 안 온다.

**`CLUSTER_H` 스윕 (V 0.70 고정)**
```
0.05 → 14/14      0.20 → 14/14      0.32 → 13/14   ← 여기서 무너짐
0.10 → 14/14      0.25 → 14/14      0.40 → 13/14
0.15 → 14/14 ★    0.30 → 14/14
```

**0.30 은 무너지기 «바로 직전»이었다.** 0.15 를 쓴다 — 낮을수록 「정말 한 동네일 때만 착지」다.
뒤집히는 방향이 「칩이어야 하는데 착지」이고, 그게 Laban 외 2025 의
*"prematurely attempt to generate final solutions"* 다.

## 3-2. V ent 가 틀린 2건 — 「같은 것을 다르게 말한 것」

```
🔴 「용접 일을 하고 싶어요」        V=0.887(칩)  C=0.000  묶음 1개
   상위: 용접공통직무 · CO₂용접 · 로봇용접 · 피복아크용접     ← 전부 «용접»

🔴 「자동차 고치고 정비하는 일」    V=0.964(칩)  C=0.000  묶음 1개
   상위: 자동차전기·전자장치정비 · 자동차차체정비 · 자동차엔진정비 ← 전부 «자동차»
```

**콕 집어 말한 사람에게 「CO₂용접·로봇용접 중 뭐요?」를 되묻고 있었다.**

근거 — Farquhar, Kossen, Kuhn & Gal, *Nature* 630, 625–630 (2024). 저자 블로그(Oxford OATML):
> *"it doesn't distinguish between cases where the LLM has **lots of different ways to say
> the same thing**, and cases where the LLM has **lots of different things to say**."*

⚠ Nature 초록 자체는 인증 리다이렉트로 직접 확인 못 했다. 축자 인용은 저자 블로그 기준.

## 3-3. 채택한 것 — **2단 판정** (V AND C 는 «되돌렸다») ★

### 왜 처음 설계를 버렸나 — 판정이 «이진»이 아니라 «2단»이었다

처음엔 `V AND C-ent` 로 붙여 14/14 를 얻었다. **그런데 라벨이 틀렸다.**
「용접 일을 하고 싶어요」를 「카드」로 라벨했는데 **「세부 칩」이 맞다** —
CO₂용접 / 로봇용접 / 피복아크용접 중 뭐냐는 물어볼 만한 질문이다.
`V AND C` 는 그걸 카드로 직행시킨다.

**되묻기는 두 종류다:**
```
방향 칩   「돌봄 / 만들기 / 사무 중 어디?」        ← 어느 «동네»
세부 칩   「CO₂용접 / 로봇용접 중 어디?」          ← 그 동네 «어디»
```
이진 판정은 이 둘을 뭉갠다.

### 채택 — 두 신호에 «다른 일»을 시킨다

```
1단  TOP%   1위 묶음의 점유율     < 0.90  →  방향 칩
2단  V-ent  그 동네 안에서 갈리나  ≥ 0.70  →  세부 칩
                                  < 0.70  →  카드
```

**실제 코드 상수(CTOP_H=0.90 / SPREAD_H=0.70)로 14건 전부 말이 되는 판정:**

| 판정 | 질의 |
|---|---|
카드 | 빵 만드는 일 · 미용 · 간호조무사 · 어르신 요양 · 제과제빵 |
세부 칩 | **용접**(공통/CO₂/로봇) · **자동차 정비**(차체/엔진/전기) · **손으로 만드는 일**(목공예/가구/섬유) |
방향 칩 | 도움되는 일 · 컴퓨터 · 조용한 일 · 자격증 · 돈 되는 일 · 사람 상대 |

### 왜 C-ent 를 버렸나 — 숫자의 «뜻»이 안 고정된다

엔트로피는 「묶음 개수」와 「균등성」을 **섞어서** 잰다:
```
묶음 3개  C-ent = 0.015   「빵 만드는 일」            ← 같은 묶음 수인데
묶음 3개  C-ent = 0.952   「사람에게 도움이 되는 일」   ← 63배 차이
묶음 2개  C-ent = 0.123 ~ 0.317
묶음 4개  C-ent = 0.270 ~ 0.863
```
「묶음 몇 개냐」로도 「얼마나 몰렸냐」로도 못 읽는다.
TOP% 는 「1위 동네가 얼마나 지배적인가」 **하나만** 재서 0.90 이 「90% 이상 한 동네」로 고정된다.

⚠ `_cluster_entropy` 는 지우지 않고 `[measure]` 계측용으로 남겼다.

### 골든셋 검증 ✅

```
2단 판정 도입 후 골든셋   34 / 34   (95초, 실패 0)
2단 판정 실제 발동 확인   [itda] 한 동네(TOP%=0.970, 3묶음) — 착지
```

되돌리려면 `.env` 한 줄: `ITDA_TWO_STAGE=0`

### ⚠ 알려진 한계 두 개

**① NCS 분류가 「돌봄」을 세 대분류로 찢어놓는다**
```
일상생활기능지원   사회복지·종교 / 사회복지
가사지원          경비·청소     / 청소      ← 다른 대분류
요양지원          보건·의료     / 보건      ← 또 다른 대분류
```
사용자에겐 전부 「어르신 돌봄」인데 TOP% 가 낮게 나온다.
**대분류로 올려도 안 고쳐진다.** 임베딩으로 묶는 것도 실패:
```
요양지원 ↔ 제빵        0.742    ← 더 가깝다
아이돌봄 ↔ 요양지원     0.720    ← 같은 돌봄인데 더 멀다
```
⇒ 근본 해법은 `job_attr` 태깅(활동유형·다루는대상). 이미 1,064개 붙어 있다.

**② 검색 순위가 틀리면 신호도 못 쓴다** — 「전기 배선」에 내선공사가 안 나오는 건
클러스터가 틀린 게 아니라 **순위**가 틀린 것. 별개 문제다.

## 4-5. 출력가드 — 「자기 편 문장」을 죽이고 있었다 ★

| 검사 | 결과 |
|---|---|
`guard_test` | **14 / 14** · LLM 0회 |

**발견**: 가드가 봇의 **면책 문장 자체**를 삭제하고 있었다.
```
[itda] 출력가드: 1문장 제거 — 응시요건 단정:
       자격증의 응시 자격은 제가 단정해서 말씀드릴 수 없어요.
```
`_ENTRY_CLAIM`의 `'응시자격은'`이 부분일치했다.

**왜 중요한가** — 우리 DB에는 응시요건 원문이 없고(오염도 확인됐다), 근거 없이 「정정」을
밀면 멀쩡한 전제까지 반박한다. 남는 건 «인식적 유보»뿐인데, 그 형식의 효과는 실측돼 있다:

> Kim 외 (FAccT 2024, arXiv:2405.00623, **N=404**):
> *"First-person expressions (e.g., 'I'm not sure, but…') decrease participants' confidence
> in the system and tendency to agree with the system's answers, **while increasing
> participants' accuracy**."*

**처방을 「부정문 예외」에서 「1인칭 인식 유보 화이트리스트」로 바꿨다** ★ —
「부정문이면 살린다」로 갔으면 **「학력 제한이 없어요」(부정형 사실 단정)가 같이 살아난다.**
구별점은 부정 여부가 아니라 **무엇을 부정하는가**다.

**작업 중 한국어 ㅂ불규칙에 걸렸다** — `'어렵'` 패턴이 `'어려워요'`를 못 잡는다.

## 7. 일상 대화가 「이탈」로 끊기던 것 (2026-08-08) ★

### 7-1. 무엇이 문제였나 — 담을 칸이 없었다

실측 4턴:

| 발화 | 고치기 «전» |
|---|---|
`나 오늘 버스에서 학생들이랑 놀러다녔어` | **"저는 진로·적성 상담을 도와드려요…"** ← redirect. 대화가 끊김 |
`애들이 진짜 시끄럽더라ㅋㅋ` | "아이들을 돌보거나 가르치는 일을 해보신 적이…" |
`근데 날씨는 좋았어` | "날씨가 좋아서 다행이에요. **요즘은 아이들과 함께 시간을**…" |
`어제 잠을 못 자서 피곤해` | "무리하지 마세요. **아이들과 함께하는 일 중에서도**…" |

그리고 「학생들이랑 놀았다」에서 `관심분야=아이들` · `다루는대상=사람` 이 뽑혔다.
**오늘 있었던 일이 선호 슬롯으로 빨려 들어갔다.**

원인 — 발화 판별기의 범주가 여섯(`진로·사정·못정함·되묻기·착지요청·이탈`)인데
**「일상」이 없다.** 「버스에서 놀았다」는 진로도 사정(돌봄·건강·돈)도 아니라 **이탈**로 떨어졌다.

### 7-2. 근거

- **챗봇 대화설계 SLR** (arXiv:2301.06474, 40편 선별) Figure 2 —
  「추천」·「웰빙」 목적 챗봇은 **credulity·intimacy** 관계를 세워야 하고,
  그 수단이 **naturalness**(self-introduction, **small talk**, echoing, casual language)와
  **emotionality**(emphatic messages, humor)다.
  그리고 **피해야 할 것 1번이 `Repetitive messages`**.
  > the positive effect of textual practices are harmed by the **lack of variability in messages**
  > causing users to see the chatbot as **"an auto-machine"**
- 같은 문헌: small talk 은 **"important to control"** — **금지가 아니라 통제**다.
- **작업동맹**(Bordin 1979 · Whiston 외 2016 메타분석): 작업동맹과 진로상담 성과의
  상관 **r = .30**. 작업동맹은 「정서적 유대」를 포함한다.
  ⇒ **일상 대화는 낭비가 아니라 성과의 일부다.**

### 7-3. 고친 것 — 생각보다 작았다

판별기 결과의 소비처가 **하나뿐**이었다:
```python
async def on_factor(...)  # on_topic
    return (await self.utt_kind(user_msg)) != '이탈'
```
**여섯 범주를 만들어 두고 「이탈이냐 아니냐」만 쓰고 있었다.**
⇒ 「일상」을 **추가만 해도** redirect 가 사라진다.

| 위치 | 변경 |
|---|---|
`prompts.py` GATE_ONTOPIC | 「일상」 범주 신설 — **정보 «요구»가 아니라 «말 걸기»** 로 이탈과 가름 |
`prompts.py` `_GATE_SCHEMA` | enum 에 `'일상'` |
`itda_core.py` `utt_kind` | 화이트리스트에 `'일상'` |
`prompts.py` SYSTEM [말투] | 【일상 이야기는 «그냥 받아라»】 절 — 실측 오답 3개를 ✗ 예시로 |
`itda_core.py` | **`_llm_said_nothing` 가드** — LLM 이 선호 3축을 하나도 안 담은 턴에는 코드 보완(`fill_object_slot`·`fill_obj_detail`)도 하지 않는다 |

## 10. 「제과제빵 → 공예」를 단계별로 추적했다 (2026-08-08) ★

**증상** — 「제과제빵 배웠어요」 → 「만드는 게 재밌었어요」 에
목공예·가구제작·금속공예·도자공예·섬유공예. **제과제빵이 하나도 없다.**

### 10-1. 단계별로 재보니 — 검색도 리랭커도 «무죄»였다

**질의를 하나씩 던지면 정확하다:**

| 질의 | 상위 5 |
|---|---|
`제과제빵과 같이 손으로 만드는 일` | **제과 · 한과제조 · 제빵 · 떡제조** · 목공예 |
`제과제빵 만들기 사람` | **제과 · 제빵 · 한과제조 · 떡제조** · 식품품질관리 |
`무언가를 직접 만드는 활동` | 목공예 · 청소년활동 · 가구제작 · 도자공예 |
`손으로 제작하는 작업` | 목공예 · 줄걸이작업 · 가구제작 |
`창작물을 만드는 일` | 목공예 · 특용작물재배 · 가구제작 |

**리랭커도 정확하다** (질의 `제과제빵 만들기 사람`):

| 직업 | 벡터 | 리랭커 rr |
|---|---|---|
제과 | 0.738 | **+0.2249** |
제빵 | 0.738 | **+0.2239** |
떡제조 | 0.705 | +0.0597 |
음식조리공통직무 | 0.529 | **−0.0447** (무관 판정) |
한식조리 | 0.604 | **−0.0949** (무관 판정) |

⇒ **RRF·엔트로피·리랭커 전부 무죄.** 문제는 **RRF 에 들어가는 입력**이었다.

### 10-2. 진짜 원인 — 「닻」이 잘려나가고 있었다

`match_jobs` 는 `queries[:4]` 로 **앞 4개만** 쓴다. 그 주석:
> **앞자리가 우선**이므로 호출부는 결정론적 앵커(사용자 원문·**슬롯 질의**)를 **앞에** 두고
> LLM 변형을 뒤에 둔다 — 잘려도 앵커는 남는다.

**구현은 정반대였다.** 변형이 앞, 슬롯 질의(닻)가 뒤 → `[:4]` 에서 닻이 통째로 잘렸다.

| | 실제로 쓰인 앞 4개 | 결과 |
|---|---|---|
전 | 만드는 게 재밌었어요 · 무언가를 직접 만드는 활동 · 손으로 제작하는 작업 · 창작물을 만드는 일 | **제과제빵 0개** |
후 | 만드는 게 재밌었어요 · **제과제빵 만들기 돕기·돌봄 사람** · … | **한과제조·제과·제빵·떡제조** |

**왜 이렇게 되나** — RRF 는 「여러 순위에 공통으로 오른 후보」를 올린다.
LLM 변형 6개가 사실상 같은 뜻이면 **중복 투표**가 되어, 사용자가 실제로 말한 낱말을
다수결로 눌러버린다. 닻은 바로 그 drift 를 막으려고 만든 것인데 잘려서 못 막았다.

**고침 후 확인**: 골든셋 **34/34 · 76초**(전 82초). 검색을 건드렸는데 회귀 없음.

### 10-3. 남은 문제 — 「선택지에 대한 답」이 «새 관심사»로 기록된다 ★ 미해결

질의 순서를 고친 뒤 3턴 흐름:

```
1턴  제과제빵 배웠어요 …           → ask
2턴  만드는 게 재밌었어요           → 적응적 되물음
     🤖 "음식을 만드는 것과 나무를 다루는 것 중 어떤 쪽에 더 흥미가 있으신가요?"
3턴  음식 쪽이요                   → 🃏 음식조리공통직무 (자격증 한식·중식·일식조리기능사)
```

3턴 질의는 정상이었다 — 4개 중 3개에 「제과제빵」이 들어 있었다.
그런데 **「음식」이 관심분야에 «새 값»으로 추가**됐다(`제과제빵 음식 만들기 …`).

**봇이 물은 건 「음식이냐 나무냐」라는 이분 선택지였다.**
사용자는 「나무 말고 음식」이라고 답한 것인데, 시스템은 **「음식 일반에 관심이 생겼다」**로 읽었다.
그 결과 「제빵」이 아니라 「음식조리공통직무」가 나왔다.

⇒ **되물음에 대한 답은 «새 정보»가 아니라 «후보 중 선택»이다.** 지금은 그 구분이 없다. **미해결.**

### 10-4. 「RRF 가중치」는 **두 번째로 기각**했다 ★

`_rrf` 주석에 2026-08-04 에 이미 기각한 기록이 있었다:
> 정답이 무게 1.0→5.0 에서 **8위 → 7위로 거의 안 움직였다.**
> k=60 이면 1/61 과 1/66 이 거의 같다. RRF 는 사실상 **표 세기**다.
> **무게로 이길 수 있는 구조가 아니다.** ⇒ **질의 목록 자체를 손봐야 한다**

그 실험은 «닻이 잘려나가던 시절»에 한 것이라 **조건이 달라졌으므로 다시 쟀다**(10-2 수정 후):

| 닻 가중 | 상위 6 | 제빵/제과 순위 |
|---|---|---|
×1 (지금) | 일식조리·음식조리공통직무·아이돌봄·요양지원… | **6위 밖** |
×2 | 일식조리·아이돌봄·요양지원… | 6위 밖 |
×3 | (거의 동일) | 6위 밖 |
×5 | 일식조리·아이돌봄·요양지원·**제과**·…·**제빵** | 4위 |

**주석이 맞았다.** ×5 까지 올려야 겨우 4위고 상위엔 여전히 무관한 것이 남는다.
⇒ 가중치는 채택하지 않았다. **원인은 다른 데 있었다.**

### 10-5. 진짜 원인은 「닻 자체의 오염」이었다 ★

개별 질의를 보다가 찾았다:
```
「음식 만들기 돕기·돌봄 사람」 → 아이돌봄 · 음식조리공통직무 · 요양지원 · 가사지원
                  ↑↑↑↑↑↑↑↑↑  닻 안에 «돌봄»이 섞여 있다
```
슬롯이 이랬다 — `활동유형=[만들기, 돕기·돌봄]` · `다루는대상=[사람]`.
그 「돕기·돌봄」은 1턴 「할머니가 입원하셔서 못 갔어요」에서 온 것이고 **종류=못함**이다.
「사람」은 「할머니」를 보고 코드가 채운 것이다.

**즉 6장에서 만든 「종류」가 검색·순위에 반영되지 않고 있었다.**

| 조건 | 상위 6 | 제빵 | 돌봄 직업 |
|---|---|---|---|
종류 무시(당시) | 음식조리공통직무·제빵·**아이돌봄**·제과… | 2위 | 1개 |
「못함」 축 제외 | 음식조리공통직무·제빵·한과제조·제과… | 2위 | **0개** |
「못함」+code축 제외 | **제빵·제과**·한과제조·음식조리공통직무… | **1위** | **0개** |

**고침** — 두 가지:
1. `_slot_kind` 를 **축 단위 → 값 단위**로 바꿨다 `{슬롯: {값: 종류}}`.
   축 대표만으로는 「활동유형=[만들기(원함), 돕기·돌봄(못함)]」에서 돌봄만 뺄 수 없다.
   축 대표가 필요한 곳(`can_land`)은 `axis_kind()` 가 «무게 큰 값»을 돌려준다.
2. `wanted_vals()` 신설 — 「못함」이 아닌 값만. **검색어(`_search_query`·`_slot_queries`)와
   순위 가중(`ATTR_LIFT`) 둘 다** 이걸 쓴다.
   ⚠ 한쪽만 고치면 「검색은 안 끌려가는데 순위는 여전히 당겨지는」 상태가 된다(실측으로 확인).

⚠ **경험이 사라지는 것 아니냐** — 아니다. 「돌봄을 했다」는 사실은 대화 이력에 남고
  최종선택(`llm_pick`)이 그것을 읽는다. 여기서 빼는 것은 **검색 방향**뿐이다.

**확인** — 0원 검사 7종 유지 · 골든셋 **34/34 · 76초** · 태그 가중 로그에서 「돕기·돌봄」이 사라짐.

### 10-6. 불안정도 — **0** (같은 대화 3회 완전 동일)

온도 0.0 에서 같은 3턴을 3회 돌렸다.

### 10-7. 칩에서 「제과·제빵」이 빠지던 진짜 이유 — **확장질의(alts)가 닻을 표로 누른다** ★

```

                  · 무언가를 직접 만드는 활동 · 손으로 무언가를 제작하는 일 ]
반환            = 가구제작 · 목공예 · 한과제조 · 떡제조 · 도자공예 · 금속공예 …
```
**4개 중 3개가 「만들기」의 동어반복**이다. RRF 는 표 세기이므로 현재 턴이 3표, 누적 프로필(닻)이 1표다.

| 설정 | 상위 6 | 제과·제빵 |
|---|---|---|
지금 (원문·닻·alt2) | 가구제작·목공예·한과제조·떡제조·도자공예·금속공예 | **없음** |
닻을 맨 앞으로 | (완전히 동일) | **없음** |
닻에 2표 | 가구제작·목공예·한과제조·떡제조·사출금형제작·제과 | 6·7위 |
alt 1개로 | (닻 2표와 **완전히 동일**) | 6·7위 |
**alt 없이 (원문·닻)** | **한과제조·제과·제빵·떡제조**·가구제작·목공예 | **2·3위** |

**⇒ 순서도 가중치도 아니다. «표의 개수»만이 결과를 바꾼다.** 10-4의 결론이 여기서 재확인됐다
  (「닻 2표」와 「alt 1개」가 글자 하나까지 같은 결과다).

**⇒ RAG-Fusion 의 전제는 «서로 다른» 질의인데, 지금 alts 는 원문을 바꿔 말한 것이라
   정보를 더하지 않고 «무게»만 더한다.** 같은 것에 표를 세 번 주는 셈이다.

**미해결 — 고치기 전에 판단이 필요하다.** 후보:
  (a) 프로필에 닻이 서면 alts 를 안 쓴다   (b) alts 를 1개로 줄인다
  (c) alts 생성 프롬프트에 프로필을 넣어 «다른 방향» 질의를 만들게 한다(문헌 정합, LLM 프롬프트 변경)
  ⚠ alts 를 왜 넣었는지의 기록을 먼저 찾을 것. 1턴처럼 닻이 없을 때는 alts 가 유일한 확장 수단이다.

⇒ 페르소나를 **LLM 이 연기**하게 하고, 봇의 «실제 응답»에 반응하며 끝날 때까지 두었다.
  성격 규칙: 내성적 · 묻는 것에만 짧게 답함 · 같은 질문 두 번이면 「아까 말했는데요」 ·
  카드를 바로 안 받아들임 · 만족하거나 할 말 없으면 스스로 종료.

### 12-1. 1차 (고치기 전) — 80턴, 그중 **66턴이 헛돌았다**

```
착지 14턴 (대본일 때 1.8턴)
40턴 이후 «2턴 주기 무한 루프»:
  🤖 편의점 쪽 일을 해보셨군요. 그 일에서 그나마 할 만했던 게 어떤 부분이었어요?
  🧑 아까 말했는데요, 그냥 물건 정리하는 게 좀 나았어요.
  🤖 물건을 정리하는 일이 그나마 마음이 편하셨군요. … 함께 찾아볼까요?
  🧑 그냥 뭐, 일단 가져와 보세요.
  🤖 편의점 쪽 일을 해보셨군요. …                      ← 원점
```

**🔴 착지 요청을 40턴 동안 못 알아들었다.** 사용자가 계속 조르는데 전부 False 였다:
```

「빨리 가져와 보세요」·「네 보여주세요」·「일단 한번 봐볼게요」
```
`_LAND_REQ` 는 36개인데 「그냥보여·이제보여·바로보여」류만 있다.
⚠ 낱말을 더하는 건 답이 아니다 — 「내놔」·「줘봐」·「띄워봐」는 끝이 없다.

**고침** — 게이트 enum 에 이미 「착지요청」 범주가 있었으나 **1턴에만 돌았다.**
  ⇒ `_harm_gate`(매 턴 나란히 도는 호출)에 `착지요청` 필드를 얹었다. **비용·지연 0.**
  판정 실측 **10/10** (「물건 정리하는 게 좀 나았어요」·「잘 모르겠어요」는 아니오로 정확히 구분).
  코드는 `_asked_land = wants_land(user_msg) or profile.get('_gate_land')` 로 세 곳에 연결.

### 12-2. 2차 (고친 뒤) — **착지 14턴 → 6턴.** 그러나 데드락은 형태만 바뀌었다

### 12-3. 장기 대화에서 **환각이 실제로 났다**

```
강점성향 "인내심"                            ← 사용자가 «말한 적 없다». 봇이 지어냈다
관심분야 ["편의점", "물류센터", "편의점 알바"]   ← 같은 것을 세 이름으로 쌓았다
```
`강점성향` 은 **`verify_slots` 의 근거 검증을 받지 않는 슬롯**이다(스칼라라 다른 경로).
슬롯이 80턴 동안 «쌓이기만» 하고 정리(중복 병합)가 없다. **미해결.**

### 12-4. 장기 대화 방책은 «이미 있다» — 계층 요약(2026-08-06)

```
_facts    사실 목록 — 구간마다 뽑아 «코드가» 누적. 다시 압축하지 않는다
_summary  서사     — 매번 다시 쓴다(흐름·말투 잇기)
FACTS_HEAD 12 · FACTS_TAIL 18 → 최대 30개. 넘치면 «가운데»를 버린다
```
설계 근거(주석 축자) — 「50턴이면 2턴째의 「할머니 간병하느라 학교를 못 다녔다」가
**네 번 다시 압축된다** … 우리 사용자에게는 그 초반 정보가 **가장 안 변하고 가장 중요한 것**이다」
⇒ 초반=정체성(안 변함) · 최근=현재 관심(선명해야 함) · **흐려도 되는 건 중간.**
⚠ **LLM 호출 수는 그대로 1회**다(한 번 부를 때 요약과 사실을 같이 받는다).
  다만 «입력 토큰»은 늘어난다 — 프롬프트 캐싱(고정부 3,200토큰)이 일부만 흡수한다.

⇒ **기억 구조는 좋다. 환각과 데드락은 그것과 별개 자리다.**

## 14. RRF 의 k 를 «처음으로» 재봤다 (2026-08-09) ★

### 14-0. 왜 재나 — 우리가 고른 값이 «아니었다»

`match.py` `_rrf(*lists, k=60)` 주석은 이렇게만 적혀 있었다:

> k=60 은 RRF 표준값(상위권 격차를 완만하게 해 한쪽 검색의 잡음에 덜 흔들린다).

즉 **재보고 고른 게 아니라 관행을 그대로 쓴 것이다.** 발표에서 「k를 재봤다」고 말하면 거짓이 된다.
(사용자가 「재봤던 것 같다」고 했으나, 저장소를 전수 조사한 결과 재본 것은 **원문 가중치 1.0→5.0**
이었고 k 값 자체를 쓸어본 기록은 **없다**. `k=10`·`k=20` 같은 문자열이 저장소 어디에도 없다.)

**k 가 무엇인가** — RRF 점수 = Σ 1/(k + 순위).

| k | 1등 | 2등 | 3등 | 뜻 |
|---|---|---|---|---|
0 | 1.000 | 0.500 | 0.333 | 1등이 압도한다 |
60 | 0.0164 | 0.0161 | 0.0159 | 거의 같다 → 사실상 «표 세기» |

60 은 Cormack 외 2009 가 처음 제안할 때 쓴 값이고 이후 관행이 됐다.

### 14-1. 어떻게 쟀나 — 검색은 «한 번만» 돈다

질의마다 벡터 순위·키워드 순위를 한 번 받아 두고 **k 만 바꿔 다시 합친다.**
⇒ k 를 몇 개 재든 추가 비용이 0 이다.

```
도구      checks/rrf_k_sweep.py (신설)
질의      calibration_set.json 100개 · **원문 하나만** (다른 변수를 고정)
정답      build_calibration_set 이 만든 것 — 사람 라벨이 아니다
비용      생성 LLM 0회 · 임베딩 100회(질의당 약 30토큰) · Pinecone 질의 100회
          ⚠ 임베딩 단가는 «확인하지 않았다». 작을 것이라고 추정할 뿐 실측이 아니다
```

### 14-2. 결과

⇒ **남은 과제 1순위.** 발표 뒤 ①②③ 을 채우고 k=1 로 내리는 것을 검토한다.

**슬롯은 완벽했다.** 검색·순위도 멀쩡했다(칩이 사무행정·통계조사, 돌봄 0개).

```
실제   "…돕는 일«처럼요»"        ← 예시 나열이다. 권유도 선택지도 아니다
슬롯   못함 = 「돕기·돌봄」        ← 「다른 사람을 돕는 일」과 «글자가 다르다»
```


### 17-6. 남는 것

`LCLS_FILTER` 는 여전히 **버리는** 연산이다. 막연한 질의에서 모델이 대분류를 틀리면
같은 일이 난다(키워드가 0.00 이라 건너뛰지 않는다). 근본 해법은 `job_attr` 태그 가중처럼
**「버리기」를 「당기기」로** 바꾸는 것인데, 그건 착지 판정이 보는 순위를 통째로 흔들어
회귀를 다시 다 돌려야 한다. **발표 뒤 과제**로 남긴다.
